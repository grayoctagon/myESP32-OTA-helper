Ich habe einen OTA (Over-the-Air update) Arduino Sketch für einen ESP32-C3. Bitte schreibe mir dazu ein passendes PHP Backend inklusive Web-Frontend.

Ziel:
Erstelle eine einzige PHP-Datei namens index.php. Diese Datei soll Backend, API und Frontend enthalten. Es soll minimales CSS und minimales JavaScript enthalten sein. Alle Frontend-Aktionen sollen per AJAX abgesendet werden.

Technische Vorgaben:
- Eine einzige PHP-Datei: index.php kommentiere wo nötig
- benutze relative URLs, die Anwendung wird nicht im URL root liegen "/..." -> "?..."
- Keine Datenbank
- Persistenz ausschließlich über data.json
- Firmware-Dateien liegen im Ordner bins
- PHP 8 kompatibel
- Keine externen Libraries
- JSON-Zugriffe müssen mit flock() abgesichert werden
- data.json soll automatisch angelegt werden, falls sie fehlt
- Schreibvorgänge auf data.json sollen möglichst atomar erfolgen
- Fehler sollen als JSON mit success:false zurückgegeben werden
- Frontend soll HTML, minimales CSS und minimales JS direkt in index.php enthalten

ESP-Authentifizierung:
- ESPs authentifizieren sich nur über ihre MAC-Adresse. (Mir ist bewusst, dass das unsicher ist. Bitte keine zusätzliche ESP-Authentifizierung einbauen.)
- ESPs haben nur read-only Rechte.
- ESPs dürfen nur die für sie ausgewählte Firmware herunterladen.
- Jeder ESP-Besuch wird in data.json protokolliert.
- recentVisits werden je ESP auf logLimit begrenzt.
- Unbekannte ESPs werden automatisch aufgenommen, solange maxKnownESP nicht erreicht ist.
- Das Label eines neuen ESP lautet: "new ESP at <iso time>"
- nextFirmwareFile ist bei neuen ESPs standardmäßig false.
- Wenn maxKnownESP erreicht ist, soll ein unbekannter ESP dieselbe Antwort bekommen wie ein bekannter ESP ohne verfügbare Firmware: "no new firmware available" (Dadurch soll Angreifenden nicht erkennbar sein, ob ein neuer ESP angelegt wurde oder nicht.)

Firmware-Logik:
- Eine neue Firmware wird nur angeboten, wenn sie jünger ist als lastFirmwareDownloadT des jeweiligen ESP.
- Wenn nextFirmwareFile false ist, wird keine Firmware angeboten.
- nextFirmwareFile kann entweder false, "*<filename>" oder eine konkrete Versionsdatei sein.
- "*<filename>" bedeutet: neueste Version dieser Firmware-Datei verwenden.
- Wenn ein Admin die Firmware-Zuweisung für einen ESP ändert, muss lastFirmwareDownloadT auf false gesetzt werden, damit die Firmware bei der nächsten Anfrage sicher angeboten wird.

Firmware-Dateien:
- Uploads landen im Ordner bins.
- Für jede Firmware gibt es einen Unterordner mit dem normalisierten Dateinamen.
- Erlaubte Zeichen für Ordnernamen und Dateinamen: A-Z, a-z, 0-9, Punkt, Bindestrich, Unterstrich und Plus.
- Der gespeicherte Dateiname bekommt vorne einen ISO-Zeitstempel, wobei Doppelpunkte durch Unterstriche ersetzt werden.
- Beispiel Uploadname: "Esp32c3_Ota_test.ino.bin" -> Speicherpfad: "bins/Esp32c3_Ota_test.ino.bin/2026-05-31T16_57_37.849+02_00_Esp32c3_Ota_test.ino.bin"
- Uploads sollen in data.json unter files gespeichert werden.
- Im Frontend sollen alle Firmware-Dateien inklusive Versionen angezeigt werden und herunterladbar sein.
- der direkte download aus dem bins ordner soll via .htaccess verboten sein (besteht die datei ".htaccess" nicht soll sie erstellt werden)

Firmware download:
- PHP darf keine zusätzlichen Bytes ausgeben. Das ist bei OTA extrem wichtig. Vor oder nach der Binary darf nichts stehen, also kein HTML, kein Whitespace, kein BOM, keine PHP-Warnings. Vor readfile() am besten Output-Buffer leeren mit "while (ob_get_level()) {ob_end_clean();}". Und Fehler nicht an den Client ausgeben: "ini_set('display_errors', '0');"
- wird eine Frimware zum download angeboten, soll der Header das enthalten: 
HTTP/1.1 200 OK 
Content-Type: application/octet-stream 
Content-Length: <firmware-size>

Token-System:
- Frontend und Uploadschnittstelle authentifizieren sich per Token.
- Tokens werden nicht im Klartext gespeichert.
- In data.json stehen nur password_hash() Hashes.
- Prüfung erfolgt mit password_verify().
- allowedUpload:false bedeutet read-only.
- allowedUpload:true bedeutet Admin- bzw. Upload-Rechte.
- Read-only Tokens dürfen nur ihren eigenen Token neu setzen.
- Tokens mit allowedUpload:true dürfen:
  - Firmware hochladen
  - ESP Labels ändern
  - Token Labels ändern
  - andere Tokens überschreiben
  - Firmware-Zuweisungen pro ESP ändern
  - einen ESP Eintrag löschen (im frontend aber mit Bestätigung aller "sind sie sicher? <ja> <nein>" )

API-Actions:
Implementiere mindestens diese Actions über index.php?action=...
jeder Aufruf einer aktion soll in den recentVisits des esp, bzw des token geloggt werden

1. action=esp_download
   Methode: GET
   Parameter:
   - "macadress" (ja leider mit Tippfehler)
   - "currentFirmware" optional

   Verhalten:
   - lastSeenT und lastSeenISO8601 aktualisieren
   - lastFirmware aktualisieren, falls Parameter firmware vorhanden
   - prüfen, ob neue Firmware verfügbar ist
   - falls keine Firmware verfügbar ist, antworte exakt als Text: "no new firmware available" und ESP-Besuch in action_note loggen
   - falls Firmware verfügbar ist: gib diese zurück (siehe Punkt "Firmware download" die HTTP-Antwort muss sehr exakt sein) und setzt lastFirmwareDownloadT und lastFirmwareDownloadISO8601 und ESP-Download in action_note loggen

2. action=frontend_data
   Methode: GET
   Authentifizierung: token
   Verhalten:
   - gibt alle für das Frontend benötigten Daten als JSON zurück
   - read-only Tokens dürfen Daten sehen, aber keine Admin-Aktionen ausführen

3. action=upload_bin
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - file
   - label optional
   Verhalten:
   - validiert .bin Upload
   - speichert Datei im bins Ordner
   - aktualisiert files in data.json
   - loggt in recentVisits als action_note die details des uploads (den gespeicherten namen inkl datum z.B. "2026-05-31T16_57_37.849+02_00_Esp32c3_Ota_test.ino.bin" und dessen größe in Bytes)

4. action=set_esp_firmware
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - macadress des esp
   - nextFirmwareFile
   Verhalten:
   - setzt nextFirmwareFile
   - setzt lastFirmwareDownloadT auf false
   - setzt lastFirmwareDownloadISO8601 auf false
   - loggt in recentVisits als action_note die Parameter

5. action=set_label
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - type: esp, token, file oder fileversion
   - id
   - label
   Verhalten:
   - ändert das passende label
   - loggt in recentVisits als action_note die Parameter

6. action=change_token
   Methode: POST
   Authentifizierung: token
   Parameter:
   - targetTokenHash
   - newToken
   Verhalten:
   - read-only darf nur eigenen Token ändern
   - allowedUpload:true darf andere Tokens ändern
   - neuer Token wird mit password_hash() gespeichert

7. action=delete_esp32
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - macadress des esp
   Verhalten:
   - entfernt den esp Eintrag aus der data.json

8. action=delete_token
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - targetTokenHash
   Verhalten:
   - entfernt den token Eintrag aus der data.json

9. action=create_token
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - targetTokenSecret
   - Label
   - is_allowedUpload
   Verhalten:
   - erstellt token Eintrag in der data.json
   
10. action=mkBackup
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter: keine
   Verhalten:
   - erstellt ein Backup der data.json im ordner "dataBackups" und hängt vor dem tateinamen den ISO 8601 an z.B. "2026-05-31T16_57_37.849+02_00_data.json"
   - stellt sicher, dass es im "dataBackups" ordner eine .htaccess gibt, wenn nicht wird diese erstellt, so dass es alle zugriffe verbietet

11. action=change_logLimit
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - new_logLimit
   Verhalten:
   - ändert das logLimit
   - loggt in recentVisits als action_note das alte und das neue logLimit
   
12. action=change_maxKnownESP
   Methode: POST
   Authentifizierung: token (nur die mit allowedUpload:true)
   Parameter:
   - new_maxKnownESP
   Verhalten:
   - ändert das maxKnownESP
   - loggt in recentVisits als action_note das alte und das neue maxKnownESP Limit

Frontend:
- Das Frontend soll in derselben index.php enthalten sein.
- Beim Laden fragt das Frontend per AJAX action=frontend_data ab.
- Falls der Tocken nicht via GET-PArameter übergeben wurde, gibt es ein Token-Eingabefeld, beim bestätigen wird es der URL angefügt.
- Es gibt eine Übersicht aller ESPs.
- Bei jedem ESP anzeigen:
  - MAC
  - Label in Klammern neben der MAC
  - lastSeen
  - lastFirmware
  - lastFirmwareDownload
  - nextFirmwareFile
  - ein "🗑️" icon zum löschen des ESP (muss via window.confirm() bestätigt werden)  (wird nur angezeigt wenn allowedUpload:true)
  - recentVisits (jeweils mit details, max-height=200px, scrollbar, ein-aus-klappbar)
- Admin-Token können ESP-Labels bearbeiten.
- Admin-Token können pro ESP per Dropdown die Firmware auswählen:
  - false
  - "*<firmware name>"
  - konkrete Versionen
- Es gibt die Möglichkeit ein Backup der data.json zu erstellen, darunter werden die vorhandenen Backups angezeigt, diese sind nicht downloadbar (wird nur angezeigt wenn allowedUpload:true)
- Es gibt eine Upload-Maske für .bin Dateien, sichtbar bzw. nutzbar nur mit allowedUpload:true.
- Es gibt am ende der seite eine Übersicht aller Firmware-Dateien und Versionen.
- Es gibt eine Übersicht der Tokens:
  - eindeutige ID = hash (wird nur angezeigt wenn allowedUpload:true)
  - Label
  - allowedUpload
  - recentVisits
- Wo immer ein Label existiert, soll es in Klammern neben dem eindeutigen Identifikator angezeigt werden.
- Admin-Token können Labels im Frontend aktualisieren indem sie auf "✏️" klicken was immer rechts vom label ist, das öffnet ein div mit Textarea in dem bereits das alte value vorausgefüllt ist.
- Read-only Tokens können nur ihren eigenen Token neu setzen (aber nicht ihr label)

Auto Reload:
- Im Frontend soll es eine Option für Auto Reload geben.
- Checkbox standardmäßig unchecked.
- Intervallfeld standardmäßig 300 Sekunden.
- Einstellung soll in localStorage gespeichert werden(damit sie nicht beim reload verloren geht).
- Die Einstellung gilt je Browser Instanz, nicht je Token.
- Wenn Auto Reload aktiv ist, wird regelmäßig per AJAX neu geladen.

recentVisits Darstellung:
- recentVisits sollen visuell markiert werden.
- Jünger als 5 Minuten: grüner Rahmen.
- Jünger als 1 Tag: blauer Rahmen.
- Zwischen 5 Minuten und 1 Tag: Farbverlauf zwischen grün und blau.
- Älter als 1 Tag: normale Darstellung.

Sicherheit:
- Keine Pfadmanipulation zulassen.
- Dateinamen strikt normalisieren.
- Nur .bin Uploads zulassen.
- Uploadgröße sinnvoll begrenzen (8MB).
- Niemals ungefilterte Nutzereingaben in HTML ausgeben.
- HTML-Ausgabe immer mit htmlspecialchars escapen, bzw in JS via innerText setzen.
- JSON Responses mit korrektem Content-Type senden.
- Binärdownloads mit korrektem Content-Type senden.
- Bei ungültiger Authentifizierung keine internen Details verraten.
